二、根因（三个簇，评审已批准）
------------------------------------------------------------------------
RC1（生产缺陷，唯一真 bug）：JdtlsLaunch 两处硬编码 `bin/java`（构造校验 :24、
argv 首元素 :46，同一字面量复制两处）——Windows JDK 可执行名为 java.exe，
构造校验在 Windows 上拒绝一切合法 javaHome ⇒ 依赖有效构造的 11 个用例
（JdtlsLaunchTest 9 + JdtlsPluginConfigTest 1 + JdtlsPluginTest 2）全部红。

RC2（测试面 POSIX 假设）：5 个用例依赖 POSIX 独有进程语义（TERM 可忽略、
KILL 升级阶梯、ps/pgid 专属组、TERM 不关管道），Windows destroy()=TerminateProcess
立即硬杀无此面；另 SessionTest 断言面用字面量 `/usr/bin/setsid`，Windows 的
Path 渲染用反斜杠分隔符（`\usr\bin\setsid`）→ 形状断言在 Windows 恒错。

RC3（信号退出码编码）：3 处硬编码 137/143（POSIX 128+信号编码），Windows
TerminateProcess 退出码恒 1——但断言侧其余部分在 Windows 全部通过（被测语义
是「KILL 升级收敛 / 排水到期收敛」，非编码本身）⇒ 需平台映射而非 gate。

三、修复映射（20 方法全覆盖）
------------------------------------------------------------------------
- RC1 → JdtlsLaunch 提取纯函数 `javaBinaryName(boolean windows)`（"java.exe"/"java"），
  构造与 argv 两处都调用；私有 `isWindows()` 只做 os.name 判定。
  新增 JdtlsLaunchTest.javaBinaryNameIsPlatformAware 钉死分支选择（true→.exe，
  false→java）——Windows 分支在 macOS 上可单测、可突变（评审要求的纯函数升级）。
  覆盖：11 方法。
- RC2 → 5 个 POSIX 专属用例 assumption gate（assumeFalse(Fixtures.windows())，
  沿用仓内既有 idiom）+ SessionTest 期望值由 Path 派生（不丢覆盖：`--` 分隔与
  argv 保形语义两平台同测）。覆盖：5 gate + 1 派生。
- RC3 → Fixtures.signalExit(int) 平台映射（Windows 恒 1 / POSIX 128+signal），
  JdtlsProviderBudgetTest 三处 hasValue 改调用。覆盖：3 方法。

边界登记同步：B26 措辞（bin/java Windows 为 bin/java.exe、javaBinaryName 纯函数
判定、JdtlsLaunchTest 12 项）+ stop2-provider-design.md:24 + stop3-consumer-design.md:68。
.agents/pits.md 增半句：批量 push 首次暴露新模块 = 侦察跑时点后移。
