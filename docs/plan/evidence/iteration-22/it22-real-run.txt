## E. /cancel 真观测 —— 发现一处竞态缺陷（未改码,待裁）

E1 REPL /cancel（任务 = 分 6 步写文件;开跑 8 秒后发 /cancel,取消落在 LLM 流中期;三次）
  run1 session=headless-1790125262126-a1bc
    turn/end {"reason":{"kind":"error","message":"IllegalArgumentException: stream ended without a Finish chunk","failureKind":"unknown"},"turn":1}
  run2 session=headless-1790125344068-a062
    turn/end {"reason":{"cause":"user","kind":"aborted"},"turn":1}
  run3 session=headless-1790125379728-df4
    turn/end {"reason":{"kind":"error","message":"IllegalArgumentException: stream ended without a Finish chunk",…},"turn":1}
  三次共性: stdout「已请求取消，等待收敛」+ 轮末 stats;REPL 继续运行(随后 /exit 正常, EXIT=0)
  即: /cancel 入口与 REPL 继续均成立,但 2/3 的轮以 error 收口而非 aborted

E2 一次性 SIGINT（`kill -INT` 到 JVM;python 前台驱动器发放——非交互脚本的后台作业会被 shell 置
    SIG_IGN 使信号腿无效,`set -m` 在非交互 zsh 不可用）
  run1 session=headless-1790125559644-aa34  EXIT=3  stdout 0 字节
    E:「已请求取消，等待收敛（再按一次 Ctrl-C 强制退出）」
    E:「严重: turn 1 failed」+ 裸栈: java.lang.IllegalArgumentException: stream ended without a Finish chunk
      at io.javanatic.harness.llm.ChunkAssembly.fold / at io.javanatic.harness.agentloop.AgentLoopImpl.runStepLoop
  run2 session=headless-1790125566959-b08c  EXIT=4  stdout 0 字节
    E:「任务被取消: user」
  即: 同一动作两跑给出 3(失败) / 4(取消) 两种退出码

  归因（读码,三层）:
    ① llm/openai-compat/…/OpenAiCompatAdapter.produce: catch (AbortedException e) → offer(queue, new End())
       —— 取消被收敛为队列里的「干净流尾」
    ② 同文件 ChunkIterator.hasNext: checkAbort() 只在每轮循环顶调用（:306）;拿到 End 即 return false（:311-313）
       —— 取消若落在消费者阻塞于 queue.poll(100ms) 的窗口内,End 先被消费,此后不再有 checkAbort
    ③ core/agent-loop/…/AgentLoopImpl.runStepLoop: 流结束 → ChunkAssembly.fold(collected) 无 Finish → 裸 IAE
       → catch (RuntimeException) 归失败 → turn/end(error) → 一次性路径 exit 3（REPL 路径渲染「turn 失败」）
  影响: 违反 USAGE「取消…以 turn/end(aborted) 落账」与退出码 4 契约;脚本 `case $?` 判取消会读到 3。
        本场景 5 次观测命中 3 次（流中期取消几乎必现两分其一）。
  既测盲区: OpenAiCompatAdapterTest.cancelMidStreamThrowsAborted 是「先取消、后取件」——循环顶 checkAbort 必炸,
        覆盖不到「End 已入队、消费者正在 poll」这条分支（HeadlessSigintTest 用进程内信号 + 桩模型,同样不经过该时序）。
  修复方向（两处皆一行,未实施）:
    (a) 消费端: End 分支补一次 signal.checkAbort()（无取消 → 原样 return false,正常流尾不受影响）
    (b) 生产端: produce 的 AbortedException 分支改 offer(new Failed(e)) —— 显式承取消,由消费者原样抛出
    建议 (a)+(b) 取 (a)（消费边界统一裁决「流尾是否可信」）,配套一条「取消落在 poll 窗口内」的适配器单测。
