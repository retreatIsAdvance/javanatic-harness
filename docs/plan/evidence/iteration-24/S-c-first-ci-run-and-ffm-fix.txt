== 3. 根因：FFM 蹦床的全 long 句柄 vs 调用点的 int 实参（invokeExact 无隐式加宽） ==
- 蹦床：`Landlock.Native.SYSCALL`＝libc `syscall` 的 FFM downcall，描述符
  `FunctionDescriptor.of(JAVA_LONG, JAVA_LONG×6)` + `Linker.Option.firstVariadicArg(1)` +
  `Linker.Option.captureCallState("errno")` ⇒ 句柄静态类型 `(MemorySegment,long,long,long,long,long,long)long`。
- `MethodHandle.invokeExact` 要求**实参静态类型与句柄类型逐位一致**（不做 int→long 隐式加宽）。
- 缺陷点：`restrictSelf(int rulesetFd)`（Landlock.java:566 的 invokeExact 行）与
  `addPathBeneathRule(int rulesetFd, …)`（:557）以 `int` 直接喂 fd ⇒ FFM 层即抛
  WrongMethodTypeException，**调用根本没到内核**；异常被 restrict() 的 catch 归为
  `native call failure` → exit 13。
- 为何直到 CI 首跑才暴露（「首次真跑」定位）：
    · darwin 本机：无 landlock，Linux 腿平台分区跳过（LandlockTest 17/0/0/1）；
    · 本机容器：内核未编译 CONFIG_SECURITY_LANDLOCK，`--probe` 在 `gate()` 即返 exit 10，
      apply 路径（restrict → add_rule/restrict_self）不执行（S-c 补验档 §2）；
    · CI 步骤 6：e2e 因探针失败静默跳过（§1 判读）。
  ⇒ 本次 CI 步骤 7 是 **apply 路径在任何环境上的首次真实执行**。
- 同蹦床的其余事实（本次一并确认，非推论）：
    · `createRuleset(long)` / `prctlNoNewPrivs()` 等调用点在 CI 上真跑成功——gate() 通过、
      限制前写正对照通过、createRuleset 真建出 ruleset fd（否则报错行不会是 restrictSelf）；
    · ⇒ runner 内核确有 landlock 且 **ABI ≥ 3**（内核接受了 WRITE_EFFECTS_V1|REFER|TRUNCATE 全集）。
      「正支路环境能力」在 CI runner 上成立；缺的只是修好调用点后重跑。

== 4. 修法（已获放行：参数改 long + 每绑定一条真跑用例 + 台账回填） ==
$ git diff sandbox/local/src/main/java/io/javanatic/harness/sandbox/local/Landlock.java
-    private record CallResult(long value, int errno) {
+    record CallResult(long value, int errno) {
-    private static CallResult addPathBeneathRule(int rulesetFd, int parentFd, long allowed) throws Throwable {
+    static CallResult addPathBeneathRule(long rulesetFd, int parentFd, long allowed) throws Throwable {
-    private static CallResult restrictSelf(int rulesetFd) throws Throwable {
+    static CallResult restrictSelf(long rulesetFd) throws Throwable {
+        // 全 long 形参：invokeExact 要求实参静态类型逐位一致（无隐式加宽），故调用点 fd 一律以 long 传入。
（置于 SYSCALL 句柄声明上方）
# 取舍：调用点 cast 也能过，但把 fd 形参定为 long，纪律写进类型、不散落在调用点；
#   上层 `restrict()` 的 `int rulesetFd = (int) created.value()` 与 `addRootRule(int rulesetFd, …)`
#   保持不变——Java 方法调用处的 int→long 是合法静态加宽，蹦床边界处已是 long。
# 可见性同步放宽为包私有：新增用例与产品同包，直接真调这两个内核调用点。
新增用例（LandlockTest）：

  以非法 fd（-1）真调 restrictSelf / addPathBeneathRule，断言裁决出自**内核**：
    value == -1 且 errno ∈ {EBADF(9), ENOSYS(38)}（后者为无 landlock 内核的合法档）
  ——若调用点类型纪律再破，异常落在 FFM 层（WrongMethodTypeException），断言即红。
  范围说明：同一蹦床承载 create_ruleset(444)/add_rule(445)/restrict_self(446) 三号；
  本用例真跑覆盖两个带 fd 的调用点（createRuleset 由 gate/acceptedRights 路径真跑覆盖）。

== 7. 业界方案核对（FFM 绑定选型复核，回答「有没有更好的方案」） ==
在本机容器（ubuntu:24.04 / glibc 2.39）实查：
$ nm -D /lib/aarch64-linux-gnu/libc.so.6 | grep -E 'landlock|syscall|prctl'
  ...只有 `syscall` 与 `prctl`，**无任何 `landlock_*` 符号**
判读：landlock 无 libc 包封（man-pages landlock(7) 指定 `syscall(SYS_landlock_create_ruleset, …)`；
  内核文档只给 C 示例 `samples/landlock/sandboxer.c`）⇒
  · jextract / libc 包装：包来包去还是同一个 `syscall()` 蹦床，不消除本类缺陷面，只增生成物与
    头文件依赖（且需 libc 头/版本绑定）；
  · JNA / invokeWithArguments：引入装箱与类型检查绕过，且 `captureCallState("errno")` 的
    errno 捕获直通要重新造轮子；`invokeWithArguments` 反而**掩盖**本缺陷（会做隐式转换）⇒ 更差；
  · 原生 helper（C/musl）：it24「不做」清单已钉死（FFM 分支为选中路线）；且真引入原生构建链。
结论：**维持 FFM 绑定**，本轮加固的是调用点类型纪律 + 每绑定一条真跑用例（§4）——
  这正是本缺陷的正确修法而非换机制。

== 9. 第二轮暴露的测试缺陷：errno 期望未按内核查序分档 ==
决定性输出（build 步骤 6，LandlockTest 内）：
[ERROR] Tests run: 18, Failures: 1, Errors: 0, Skipped: 2 <<< FAILURE! -- in io.javanatic.harness.sandbox.local.LandlockTest
[ERROR] io.javanatic....bogusFdReachesTheKernelInsteadOfFailingAtInvokeExact -- Time elapsed: 0.063 s <<< FAILURE!
java.lang.AssertionError:
Expecting actual:
  1
to be in:
  [9, 38]
	at io.javanatic.harness.sandbox.local.LandlockTest.bogusFdReachesTheKernelInsteadOfFailingAtInvokeExact(LandlockTest.java:207)
# 即 `restrictSelf(-1)` 在 runner 内核上给出 errno 1（EPERM），断言只认 {9 EBADF, 38 ENOSYS}。
内核查序（上游 `security/landlock/syscalls.c`，逐字引用）：
  landlock_restrict_self：先 `if (!(flags & …NO_NEW_PRIVS) && !task_no_new_privs(current) &&
      !ns_capable_noaudit(current_user_ns(), CAP_SYS_ADMIN)) return -EPERM;` —— **在取 ruleset fd 之前**；
      之后才 `ruleset = get_ruleset_from_fd(ruleset_fd, FMODE_CAN_READ)`（fd 非法 → EBADF）。
  landlock_add_rule：`is_initialized()` → flags 校验 → **先取并校验 ruleset fd**（`get_ruleset_from_fd`，
      非法 fd → EBADF）→ 再按 rule_type 分派。
判读：普通 JVM 既无 no_new_privs 也无 CAP_SYS_ADMIN ⇒ 在**真有 landlock 的内核**上
  `restrict_self(-1)` 恒给 EPERM，EBADF 分支根本到不了；本机两个环境（darwin 无 landlock、容器内核
  未编译 landlock）都只会给 ENOSYS/缺档 ⇒ 该期望**只有 CI 能证伪**，本地红绿对无法覆盖此分支。
另注：LSM 未启用档给 EOPNOTSUPP(95)，系统调用号不存在档给 ENOSYS(38)——分档随内核状态而定。
