# 0010 双臂验收 token 判据修正：降级为只报告

日期：2026-11-09。裁决人：用户（it31 双臂验收执行中自我修正）；追认：AI（结构性地板论证成立）。

## 背景

it31 四确认裁定③原定双臂判读三量纲：总 token ≤2×、父上下文降 ≥50%、墙钟只报告。双臂全量数据（12 任务对 + H 放大对）实测：价值主张决定性达成（H 对父上下文 −61.6%），但总 token 全规模 3.45×，未达 2×。

## 裁决（推翻对象）

**推翻**：裁定③的「总 token ≤2×」判据。
**替代**：token 与墙钟同档——**只报告不判赢**；赢的判据 = 父上下文降 ≥50%（族级中位数）+ 成功率持平（委派臂不低于单臂）。

## 为什么（数据归因）

2× 阈值未计入**每 agent 固定上下文成本 × (N+1)**：4 个 agent 各背 ~13k（schema + 系统提示）基线。控制实验（H2 waitSeconds 教学对照：父 100k→87k，忙轮询仅解释 −13%）证明开销是**结构性地板**而非行为可修：微任务纯 3.6× 开销，放大任务也无法低于 ~3×。判据若维持 2×，等于给「委派的价值在上下文保护而非 token 节约」这一设计立场设置永远不可达的门槛。

## 边界发现（随档）

「多小不该用」有了数字：**单臂规模 ≥~40k token 委派收益才开始显现**（H 对 55.1k→价值兑现；P/S 对 14–63k 为开销区）。这是指导使用的一手数据，入 `stop3-dual-arm.txt`。

## 影响面

- `docs/plan/iteration-31.md` 四确认裁定③段订正（同提交）
- 后续同类验收（W 段及以后）沿用修正判据；token 永远入报告列
- 挂账 it32：问态可发现性提示、delegate 工具描述引导 waitSeconds（本轮实用中发现的引导缺口）
